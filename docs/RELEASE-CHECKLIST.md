# Before making Brutal OP25 public

- Obtain a Brutal OP25-specific RadioReference application key and confirm with RadioReference that distributing it in a downloadable client image is permitted. Its current compiled encoding is recoverable; a public image cannot keep a client-side key private. Each user must still authenticate with their own eligible account. See the [RadioReference API policy](https://support.radioreference.com/hc/en-us/articles/18844460198932-Database-Web-Service-API).
- Review `tests/live-bexar-system.json` and the screenshots for RadioReference data redistribution rights and any information that should not be published. The live fixture is deliberately kept for regression coverage in this private repository; moving it into `tests/` does not change its contents.
- `LICENSE` and `THIRD-PARTY-NOTICES.md` are included in the source and image, with OP25/RTL source and headers retained. Before public distribution, verify the exact tagged image contains those files and the corresponding source/patches remain accessible to recipients; independently review any additional dependencies or copied assets introduced later.
- Verify the public `bootstrap/` installer can fetch the source archive and release image without GitHub, Git, SSH, or Docker account authentication. Local-archive install and failed-update rollback tests pass, but the private repository and image prevent the anonymous test today. On a fresh Windows machine, confirm Ubuntu WSL and Docker Engine install with one guided consent and no Docker Desktop. Then test a fresh native Linux install with no existing Brutal OP25 state.
- Before publishing the bootstrap commands, switch their mutable `main` source-archive URL to an immutable release tag (or a release asset) and publish a verified source-archive digest. Keep program-file rollback and versioned image rollback tests in that release workflow.
- Test saved-system backup and restore on the release image. The transfer passed with disposable Docker volumes; confirm Windows Documents output, native Linux output, and migration to a second clean machine. Do not restore into an active receiver session.
- Measure compressed release download and disk use. The current local image reports approximately 2.15 GB unpacked; a local `docker image save | gzip -1` stream was about 464 MB (not an exact GHCR transfer size). GNU Radio packages dominate. Do not remove SDR or plotting dependencies until receiver and plot tests prove they are unnecessary.
- Test clean Windows with no WSL or usbipd-win: approve only the guided prompts, restart if requested, and confirm RTL-SDR Blog V4 control-channel lock and browser audio without manual driver commands. Confirm the Start-menu shortcut relaunches the same Ubuntu-local Docker volume.
- Test RSPdx-R2 separately on clean Windows and supported native Linux: conditional SDRplay license, verified vendor download, private addon build, API/Soapy load check, physical device recognition, control-channel lock, and clear audio. Do not count a software-load check or OP25 startup alone as reception validation.
- The local Ubuntu WSL Engine smoke test confirmed RTL Blog V4 tuner identification and a short 1 MSPS stream with zero reported loss. A separate temporary AARRS Northeast profile achieved live P25 control-channel lock (WACN 0x91F78, system 0x0D2, site 50.50, NAC 0x3C, roughly 798 TSBKs); its temporary profile was archived after testing. Browser audio was not independently checked on this path. The RSPdx-R2 was forwarded and its exact serial/vendor/product appeared in Ubuntu. Earlier Docker Desktop tests confirmed its API/Soapy serial identification and a three-second sample stream; repeat driver and reception testing on the new WSL Engine path. Keep on-air and clean-host tests distinct from these narrower results.
- Test a Blog V3 or older RTL-SDR before claiming its preset hardware-validated; the bundled V4-capable library is vendor-documented as backward-compatible, but that has not been exercised on this project hardware.
