SDR support and validation boundaries

The receiver runs on Linux, including a dedicated Ubuntu WSL Docker Engine on Windows.
Windows RTL-SDR USB forwarding and local SDRplay streaming are handled by Launch-Brutal-OP25.cmd; native Linux uses
install-brutal-op25.sh, which enters brutal-op25.sh. Neither launcher exposes
the whole USB bus or a Docker socket to the receiver container.

Selectable presets are RTL-SDR (Blog V1-V3 / other non-V4), RTL-SDR Blog V4,
SDRplay RSPdx-R2, and custom.
Other gr-osmosdr backends are not presented as tested hardware presets.

RTL-SDR Blog V4: the base image builds the pinned rtl-sdr-blog driver at
aed0ea19f3a273370a13c9009b96313c75d54c7b. One local V4 received clear
speech from AARRS Northeast Simulcast through Windows/WSL/Docker. This does
not prove compatibility with every host, antenna, USB controller, or system.
An isolated no-profile hardware smoke test also forwarded this V4 to the
container, opened it with rtl_test, identified the V4 tuner, and detached it.
The new Ubuntu WSL Engine path repeated that test at 1 MSPS with zero reported
sample loss over a short run. A fresh manual AARRS test profile then decoded
the live Northeast Simulcast control channel (WACN 0x91F78, system 0x0D2,
site 50.50, NAC 0x3C, hundreds of TSBKs). The user later confirmed clear
browser speech on this Ubuntu WSL path. The temporary profile was archived afterward.
The same isolated test captured a three-second 1 MSPS stream through GNU Radio.
The vendor says this updated driver is backward-compatible with Blog V3 and
older generic RTL-SDRs, but those models still need a real hardware test here.
No separate Windows SDR driver or host Linux RTL package is installed by our
launcher: the Linux driver is inside the base image, while Windows only needs
the guided USB bridge to forward the selected device to WSL.

SDRplay RSPdx-R2 on Windows/WSL: USB forwarding through WSL limited this radio
to about 0.37 MSPS in a 2 MSPS test and prevented P25 control-channel decode.
The guided launcher instead uses SDRplay's official Windows API with the
open-source rsp_tcp server, bound to the local WSL virtual network interface.
The Linux base image receives that sample stream at 1 MSPS without a private
SDRplay addon. On one RSPdx-R2 with antenna A, the normal launcher decoded
AARRS Northeast Simulcast: WACN 0x91F78, system 0x0D2, site 50.50, NAC 0x3C,
hundreds of TSBKs and live talkgroup call entries. Browser audio on this path
has not yet been checked by listening, nor has a clean Windows host been tested.
The server is open-source and its matching source and license are in
../install/vendor/rsp-tcp/; the proprietary SDRplay API is not in the repo or
public image. A first-time Windows install downloads SDRplay's official API,
verifies its pinned checksum and signature, and requires explicit license
acceptance. A changed vendor download requires project review before use.

SDRplay RSPdx-R2 on native Linux: the private addon uses the official Linux
SDRplay API and SoapySDRPlay3. An isolated no-profile smoke test identified
the selected device and serial and captured a three-second 2 MSPS stream.
Control-channel lock and clear audio on native Linux have not been verified.
The proprietary addon is built on the user's computer after license review;
do not redistribute it without permission. See SDRplay-EULA.txt and
INSTALLATION-PRIVACY.txt.

Presets are starting settings, not hardware verification. Check USB visibility,
driver operation, control-channel lock, and audio on the actual receiver host.
The terminal's radio check reports software and USB readiness; it does not
prove reception. Encrypted voice cannot be decoded.

Pinned driver and patch details are in DRIVER-NOTES.txt. Active setup and
dashboard instructions are in ../README.md and BRUTAL-OP25.txt.
